# Review Report

## 1. Мёртвый код

- **Место:** `style.css:116` (`li > label { width: 226px; }`)
- **Проблема:** Правило не применяется. У лейбла задачи класс `task-label`, а `.task-label` задаёт `width: 56%` (`style.css:28-33`). Специфичность класса (0,1,0) выше, чем у `li > label` (0,0,2), поэтому `226px` никогда не выигрывает. Автор правит «ширину лейбла в списке» в одном месте и не видит эффекта — править нужно другое правило.
- **Условие:** Любая задача в списке Todo или Completed: и статическая из HTML, и созданная через `createNewTaskElement`.
- **Проверка:** В DevTools у `label.task-label` computed `width` должен совпадать с тем правилом, которое вы оставили единственным. После удаления мёртвого `width: 226px` внешний вид лейблов не должен измениться.

- **Место:** `style.css:118-120` (`li > input[type='text'] { width: 226px; }`)
- **Проблема:** Это значение не видно пользователю. Вне режима редактирования поле скрыто (`style.css:137-139`, `display: none`). В режиме редактирования побеждает `ul li.edit-mode input[type='text'] { width: 224px; }` (`style.css:141-144`). `226px` остаётся после прошлых правок вёрстки и расходится с реальной шириной поля при Save.
- **Условие:** Задача в `edit-mode` (пример: «Go Shopping» при загрузке) или после нажатия Edit.
- **Проверка:** Включить Edit и в computed styles у текстового поля должна быть одна ширина. Удаление правила с `226px` не должно сдвигать поле; если сдвинуло — живым было другое правило, не это.

- **Место:** `style.css:28-33` (селектор `.task-input, .task-label` и свойство `width: 56%` у `.task-input`)
- **Проблема:** Для `.task-input` `width: 56%` перекрыт везде, где класс используется: у поля «Add Item» — `input#new-task { width: 318px; }` (`style.css:94-96`), у поля задачи — правила выше. В группе с `.task-label` свойство выглядит общим, хотя на инпуты не действует. `display: inline-block` в том же блоке тоже не работает: родители `.add-task-form` и `li` — `display: flex`, flex-элементы игнорируют `inline-block`.
- **Условие:** Открытие страницы и сравнение computed styles у `#new-task`, `.task-input` внутри `li` и `.task-label`.
- **Проверка:** Убрать `width` у `.task-input` (оставить у `.task-label`, если процент нужен лейблу) и `display: inline-block` — ширины полей и лейблов не меняются. Если лейбл скакнул, живым был только его `width: 56%`.

- **Место:** `index.html:19` (`id="add-task-section"`)
- **Проблема:** Идентификатор не читается ни в `app.js`, ни в `style.css`. Заголовок «Add Item» стилизуется через `label[for='new-task']`. Лишний id создаёт ложное ощущение, что к секции есть привязка в логике или стилях.
- **Условие:** Поиск по проекту: `add-task-section` встречается один раз — в самой разметке.
- **Проверка:** Удалить id, страница выглядит так же, скрипт не обращается к элементу по этому имени.

## 2. Дублирование обработчиков

После делегирования на списках отдельных `addEventListener` на каждой задаче нет: `click` и `change` висят на `#incomplete-tasks` и `#completed-tasks`. Это принятое решение, замечаний по нему нет.

Оставшееся — не дублирование обработчиков, а разрыв одного сценария «добавить задачу»:

- **Место:** `app.js:80` (`addButton.addEventListener('click', addTask)`), поле `#new-task` в `index.html:21`
- **Проблема:** Добавление задачи подписано только на клик кнопки Add. Enter в поле ввода не вызывает `addTask`. Пользователь ожидает тот же обработчик, что и у кнопки, и считает, что форма сломана.
- **Условие:** Фокус в `#new-task`, непустой текст, клавиша Enter (без клика по Add).
- **Проверка:** Enter добавляет задачу в Todo так же, как клик по Add: пустая/пробельная строка не добавляется (`app.js:29`), поле очищается. Повторная подписка на `click` у кнопки не нужна.

## 3. Дублирование логики

- **Место:** `index.html:25-42` (три `<li>` с чекбоксом, лейблом, полем, Edit, Delete) и `app.js:10-26` (`createNewTaskElement`)
- **Проблема:** Одна и та же структура задачи описана в разметке и в фабрике. Новые задачи идут только через JS, стартовые — только через HTML. Если добавить атрибут, класс или вложенный узел в одном месте и забыть другое, поведение разъедется: часть задач будет без нужной разметки для `editTask` / `deleteTask` / CSS.
- **Условие:** Сравнить «Pay Bills» (HTML) с задачей, добавленной через Add. Сейчас они совпадают; расхождение проявится при следующем изменении разметки только в HTML или только в JS.
- **Проверка:** Любое изменение состава строки задачи (например, класс на чекбоксе) видно и у стартовых пунктов, и у пункта, добавленного кнопкой Add. Селекторы в `editTask` (`input[type=text]`, `label`, `.edit-button`) находят те же узлы в обоих случаях.

- **Место:** `style.css:28-33`, `94-96`, `112-120`, `141-144` (ширины `56%`, `318px`, `226px`, `224px`)
- **Проблема:** Ширина текста задачи задана несколькими магическими числами, которые почти совпадают, но не равны. В режиме Edit поле становится `224px` вместо `226px` / `56%`, строка «прыгает». Поле Add (`318px`) не связано с шириной списка (`500px`) и кнопкой (`60px`). Правка «выровнять текст задач» требует согласовать четыре правила, иначе поедет только один режим.
- **Условие:** Переключение Edit/Save у «Pay Bills»; сравнение ширины лейбла и поля; сравнение поля Add с лейблами списка на ширине окна больше 768px.
- **Проверка:** Лейбл и поле редактирования одной задачи занимают одну и ту же ширину, без сдвига кнопок. После изменения одной константы ширины колонки текста меняются и просмотр, и редактирование.

- **Место:** `app.js:38` (`listItem.querySelector('input[type=text]')`) против класса `.task-input` в `index.html` и `app.js:16`
- **Проблема:** Поле задачи помечается классом, а `editTask` ищет его по типу. Два способа сказать «это поле текста задачи». Второй текстовый `input` внутри `li` (если появится) сломает редактирование без ошибки в консоли: `querySelector` возьмёт первый попавшийся.
- **Условие:** Сейчас в `li` одно текстовое поле — баг скрыт. Проявляется, если в строку задачи добавить ещё один `input type="text"` или сменить тип/класс только в одном месте.
- **Проверка:** `editTask` читает и пишет то же поле, что стилизуется как `.task-input`. Поиск по проекту: один селектор для этого узла, и он совпадает с разметкой фабрики и HTML.

- **Место:** `style.css:7-11` (`.banner`) и `style.css:24-27` (`.main-content`)
- **Проблема:** Одинаковые `width: 500px; margin: 0 auto` скопированы. Колонка баннера и колонка списка должны совпадать визуально. Изменение ширины только у одного блока ломает выравнивание с картинкой матрицы, хотя оба блока задуманы как одна колонка.
- **Условие:** Ширина окна больше 500px; изменить `width` только у `.banner` или только у `.main-content`.
- **Проверка:** Правые края картинки и списка задач совпадают. Одно изменение ширины колонки сдвигает оба блока.

## 5. Комментарии

- **Место:** `app.js:17` (`//innerText encodes special characters, HTML does not.`)
- **Проблема:** Комментарий пересказывает, зачем взяли `innerText`, хотя код уже ставит `innerText`, а не HTML. Он не объясняет доменное правило, спорен по смыслу (`innerText` не «кодирует» в том виде, как HTML-entities) и отвлекает при чтении фабрики. Это след сравнения с `innerHTML`, а не комментарий к текущей строке.
- **Условие:** Чтение `createNewTaskElement`: строка создания кнопки Edit длиннее из-за хвоста, который не влияет на поведение.
- **Проверка:** После удаления комментария поведение Edit/Save и отображение спецсимволов в названии задачи (`<`, `&`) те же, что со `innerText`. Если нужна защита от HTML — она должна быть в коде (тот же `innerText` / `textContent`), а не в комментарии.

- **Место:** `style.css:1`, `61`, `89`, `98`, `130`, `136` (`/* Basic Style */`, `/* Heading */`, `/* New Task */`, `/* Task list */`, `/* Completed */`, `/* Edit Task */`)
- **Проблема:** Заголовки дублируют следующие селекторы: «Completed» перед `#completed-tasks`, «Edit Task» перед `.edit-mode`. Они не говорят, почему стили разбиты на блоки, и устаревают при перестановке правил (как уже произошло с `li`, который описан и в «Basic», и в «Task list»).
- **Условие:** Правка CSS: перенос правила в другой блок без обновления комментария.
- **Проверка:** Файл читается по селекторам. Если комментарий оставляют, он объясняет неочевидное (например, почему ширина поля в Edit на 2px меньше) — и это можно проверить сравнением двух состояний в UI.
