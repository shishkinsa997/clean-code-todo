# Review Report

## 1. Мёртвый код

- **Место:** `style.css:112-116` (`li > label { width: 226px; }`)
- **Проблема:** Ширина для метки задачи не применяется: у неё есть класс `.task-label`, а правило `.task-input, .task-label` на строках 28-33 задаёт `width: 56%`. Селектор класса специфичнее, поэтому значение `226px` не выигрывает в каскаде.
- **Условие:** Любая метка задачи в списках, включая статические задачи из HTML и созданные через JavaScript.
- **Проверка:** В DevTools проверить computed `width` у `label.task-label`; он должен соответствовать правилу с `56%`. Удаление `width: 226px` не должно менять отображение.

- **Место:** `style.css:118-120` (`li > input[type='text'] { width: 226px; }`)
- **Проблема:** Это значение не отображается ни в одном состоянии. В обычном режиме поле скрыто правилом `display: none` на строках 137-139, а в режиме редактирования ширину задаёт более специфичное правило на строках 141-144 (`224px`).
- **Условие:** Любое текстовое поле задачи до, во время и после режима редактирования.
- **Проверка:** Сравнить поле до и после переключения Edit/Save в DevTools; ширина видимого поля должна определяться правилом режима редактирования. Удаление значения `226px` не должно визуально менять страницу.

- **Место:** `index.html:19` (`id="add-task-section"`)
- **Проблема:** В проверяемых файлах этот идентификатор нигде не используется: на него не ссылаются ни CSS, ни JavaScript, ни ссылки внутри HTML. Это неиспользуемый атрибут, который создаёт видимость привязки секции к логике или стилям.
- **Условие:** Поиск `add-task-section` по трём проверяемым файлам находит только это объявление.
- **Проверка:** Удаление `id` не должно менять отображение или поведение страницы; поиск по проекту не должен выявить ссылок на этот идентификатор.

## 2. Дублирование обработчиков

Замечаний нет. Обработчики `click` и `change` назначены на оба списка, потому что каждый список является отдельным корнем делегирования событий. На отдельные задачи повторные обработчики не назначаются.

## 3. Дублирование логики

- **Место:** `index.html:25-42` и `app.js:10-26`
- **Проблема:** Структура строки задачи описана отдельно для начальных задач в HTML и для новых задач в `createNewTaskElement`. Сейчас эти структуры согласованы, но при изменении состава или атрибутов строки их можно обновить только в одном месте, из-за чего начальные и добавленные задачи начнут вести себя или выглядеть по-разному.
- **Условие:** Изменить разметку задачи только в HTML либо только в фабрике JavaScript, например добавить обязательный класс или элемент, который используется обработчиками или стилями.
- **Проверка:** Сравнить DOM начальной задачи и задачи, добавленной кнопкой Add: обе должны содержать одинаковые узлы и необходимые классы/атрибуты; Edit, Delete и перемещение чекбоксом должны работать для обоих вариантов.

## 4. Имена переменных и функций

- **Место:** `app.js:10, 14` (`taskString`)
- **Проблема:** Имя параметра описывает тип данных, а не назначение значения. Вызов передаёт текст задачи (`taskInput.value`), поэтому `taskString` не сообщает читателю, что это именно текст для подписи задачи.
- **Условие:** Чтение вызова `createNewTaskElement(taskInput.value)` и использование аргумента при создании `label`.
- **Проверка:** По имени параметра понятно, что передаётся текст задачи, и вызов функции читается без дополнительного выяснения роли строки.

## 5. Комментарии

- **Место:** `app.js:17` (`//innerText encodes special characters, HTML does not.`)
- **Проблема:** Комментарий неточно описывает поведение: `innerText` не «кодирует» символы, а присваивание текстового свойства не интерпретирует значение как HTML-разметку. Такая формулировка может привести к неверным выводам о защите или преобразовании текста.
- **Условие:** Чтение фабрики элемента и комментария рядом с присваиванием `innerText`.
- **Проверка:** Для названия задачи со строкой вроде `<b>&` проверить, что значение отображается как текст, а не создаёт HTML-элемент. После удаления или точного переформулирования комментария поведение должно остаться тем же.

## 6. Длинные функции

Замечаний нет. Функции в `app.js` короткие и выполняют одну понятную операцию; в частности, `createNewTaskElement` целиком читается как последовательная сборка строки задачи. Делить её только из-за числа создаваемых элементов не требуется.
